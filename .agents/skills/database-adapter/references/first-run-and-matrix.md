# Adapter setup and delivery matrix

Read this reference when adding a driver adapter, exposing database setup, or
preparing an adapter-backed module for eject or a pull request.

## Adapter descriptor

A platform adapter descriptor owns the complete first-run contract:

- an open `adapterId` and `dialectId`;
- a machine-readable configuration schema;
- UI hints such as labels, descriptions, groups, order, and input kind;
- an explicit list of secret fields;
- configuration validation without opening module databases;
- a connectivity probe with bounded time and sanitized errors;
- optional provisioning for infrastructure the adapter actually owns;
- connection creation that returns the shared adapter contract;
- advertised database capabilities.

The registry is open. Core code resolves a descriptor by id and negotiates its
capabilities rather than switching over known adapter ids, so an adapter package
can join without changing module business ports or the setup screen.

Configuration UI is generated by the platform from descriptor metadata. A
module never implements database setup UI and never asks for a DSN.

## First run

The embedded PostgreSQL is the zero-configuration local default: PGlite runs in
process, so a workstation starts with nothing installed and still exercises the
same forced row-level security a deployment enforces. Its data root comes from
the platform provider, not from each module.

Before selecting another adapter, setup:

1. validates descriptor configuration and required secrets;
2. probes the target with a strict timeout and no secret echo;
3. lists every enabled database-owning module;
4. verifies that each module declares an implementation for the target
   `dialectId` and that the adapter supplies its required capabilities;
5. refuses activation with the exact incompatible modules and capabilities;
6. provisions only after explicit operator confirmation when provisioning
   changes external state;
7. runs migrations through a migration lease before runtime leases are served;
8. verifies readiness under the non-bypass runtime role.

Secret values live in environment-backed or encrypted platform secret storage.
`flowdular.json`, module manifests, setup responses, logs, audit metadata, run
snapshots, and pull request descriptions contain only secret references or
redacted presence state.

## Switching an adapter with existing data

Changing an adapter id never points modules at an empty database and never
copies storage files. The only supported switch is an explicit operation:

1. stop writes and acquire an export snapshot;
2. export through module-owned portable records, preserving ids and versions;
3. provision and migrate the target;
4. import in dependency-safe batches under tenant context;
5. verify counts, checksums, referential expectations, and module invariants;
6. probe reads and writes through the target runtime role;
7. activate the target only after verification succeeds;
8. retain the source for rollback until the operator closes the window.

A failed import or verification leaves the source active. There is no silent
fallback to another database, because that would split writes.

## Module declarations

Each database-owning module declares:

- supported open dialect ids;
- the required capability set, such as transactions, transactional DDL,
  schema introspection, returning values, or an isolation level;
- its module-owned persistence implementation and migrations;
- one adapter-neutral repository behavior suite.

The platform compatibility check consumes these declarations before first run,
adapter change, sandbox eject, and deployment validation.

## Delivery matrix

Every turn runs against a real PostgreSQL, because the embedded one starts in
process. The sandbox and the test suites use `createTestDatabaseProvider()` from
`@flowdular/database-testing`, which brings the `coreloom_runtime` and
`coreloom_background` roles and forced row-level security with it.

A target run covers tenant A and B fixtures, operations without tenant context,
forged cross-tenant inserts, direct row-security bypass probes, concurrent
writes, and cleanup. Where a module polls across tenants, it also proves the
background role reads only the routing columns.

Before eject or a pull request the matrix additionally runs the same suite
against a server PostgreSQL when one is configured, using a unique schema and a
role that holds neither `SUPERUSER` nor `BYPASSRLS`. Test credentials are
short-lived and never enter the transcript. If that target is unavailable the
session may continue editing, and delivery states the exact missing target.

Server selection is explicit: `FD_TEST_DATABASE_ADAPTER=postgresql`,
`FD_TEST_POSTGRES_URL` (migrator), `FD_TEST_POSTGRES_RUNTIME_URL` and
`FD_TEST_POSTGRES_BACKGROUND_URL`. All three URLs are required. Missing or
unreachable configuration never falls back to PGlite. `.github/workflows/ci.yml`
runs this matrix, including auth and agents. Keep role separation intact in
fixtures: even the migration owner must supply tenant context for tenant data.
