# Deployment branding from the platform settings (2026-09-21)

Request (owner, 2026-09-21): make the backoffice name, its link preview image
and its titles, in the navigation and in the browser tab, changeable from the
platform settings. Interviewed into `system.core` 0.9.0 and approved by the
owner at SHA-256 `b1dd5a0680253a97bef8a634670636534ee425f09e175af595f8fbdf0a9b021c`.

## What landed

- Seven platform-scoped `system.core` settings: `appName`, `documentTitle`,
  `description`, `ogImageUrl`, `faviconUrl`, `themeColor`, `logoUrl`
  (`modules/system/src/settings.ts`). One identity for the installation,
  because the sign-in screen and a shared link render before a workspace is
  known. They are written through the settings administration API that already
  exists, so there is no second write path and every change is audited.
- The contract, the defaults and the bounds live in
  `packages/contracts/src/branding.ts`: a name carries no markup, quote or
  control character; an address is a same-origin absolute path or an https URL,
  so `javascript:`, `data:` and protocol-relative values are refused at the
  write; a colour is six hex digits. `applicationBrandingFrom` re-checks every
  field wherever it is read, so a stored value that no longer fits its
  declaration falls back to the product's own instead of reaching the head.
- Delivery: `installApplicationBranding` (`packages/server/src/application-branding.ts`)
  takes a provider from the module that owns the settings, the way the module
  activation gate is installed. The application route resolves it once per
  request, sets it as page state for the server render and emits one JSON data
  block plus a `--flowdular-brand` custom property for the boot splash; the
  client adopts both with `configureBrandingFromPage`
  (`packages/client/src/branding.ts`). Nothing fetches branding.
- Read at: the sidebar wordmark and the mobile header (`ShellMark`,
  `SidebarBrand`), the sign-in screen's wordmark (`AuthenticationCore`,
  auth.core 0.14.4), the boot splash, and the document head in
  `platform/src/App.tsrx` (title template, description, Open Graph, Twitter,
  `<link rel="icon">`, `<meta name="theme-color">`). The static icon and theme
  colour tags left `platform/index.html` and the scaffold template, so the head
  carries one answer instead of two.
- Screen: Administration, Branding (`modules/system/src/client/BrandingView.tsrx`),
  behind `system.settings.read`, editable with `system.settings.manage`, with a
  preview of the stored values and the five states.
- Content security policy: every https branding image origin an operator stores
  is added to `img-src` of the policy that deployment serves, including an
  `FD_CSP` of their own (`withBrandingImageSources`,
  `packages/server/src/security-headers.ts`). Without it the icon, the logo and
  the screen's own preview would be blocked with nothing in the document to
  explain why.

## Verified

`pnpm verify` and `pnpm build` are green. Live check against a development
deployment in this worktree, signed in as the seeded owner: a `javascript:`
logo is refused with `INVALID_SETTING_VALUE` and stores nothing; storing a name,
a document title, a description and a colour turns the next document into
`<title>Workspace · Acme Backoffice</title>`, `og:site_name` Acme Operations,
the new description, `<meta name="theme-color" content="#0B5FFF">`, the data
block and `--flowdular-brand:"Acme Operations"`, with no duplicate icon or
theme colour tag.

Not inspected in a browser: the rendered Branding screen and the sidebar with a
logo. The Chrome extension is not connected in this environment and Playwright
is not installed, so the evidence is the rendered HTML above plus the DOM
assertions in `shell-brand.test.tsrx`.

## Risks and follow-ups

- An application scaffolded before this release picks up the sidebar and mobile
  header automatically; its head and its boot splash follow only when its own
  `index.html` and `App.tsrx` adopt the lines the template now carries.
- A logo is an address, never an upload; per-workspace branding, colour themes,
  fonts, custom CSS and the branding of auth.core's e-mails stay out of scope.
- The TOTP issuer auth.core enrols with is still the literal `Flowdular`
  (`modules/auth/src/client/api.ts`). It is a label stored in the member's
  authenticator rather than a rendered document, so it is left for its own
  change; a rebrand would only reach new enrolments anyway.
- The faint mark behind the sign-in panel stays product art at 5 to 8 percent
  opacity; only the wordmark and the small mark beside it follow the settings.
- `modules/profile` carries a pre-existing `SPEC_VERSION_DRIFT` warning
  (module.json 1.5.4, specVersion 1.5.3) that this change neither caused nor
  fixes.
