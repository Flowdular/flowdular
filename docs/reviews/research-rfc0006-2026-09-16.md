# RFC 0006 wave 1: research, spec sections and sandbox input (2026-09-16)

The owner accepted RFC 0006 with its default variants on 2026-09-16. Wave 1
runs as three streams against one contract of fixed names; each stream
records its own section below. Stream A (`research.core` and the harness
native tool seam) adds its section when it lands.

## Stream C: sandbox input and fixtures

RFC 0006 J5 in `packages/sandbox`, with one extension point in
`packages/coding-agent` and the backend engineer role document.

### What landed

- Sample data (`server/sample-data.ts`). A session attachment ending in `.csv`,
  `.json` or `.txt` is sample data. The read-only tool `sample-data` lists each
  file with its columns, row count and a parsed preview of the first 20 rows, or
  previews one file by `name`. CSV follows RFC 4180 with a detected `,`, `;` or
  tab delimiter; JSON reads a top-level array or the first array inside an
  object; text reads lines. Bounds: 200 characters per value, 40 columns, 32 KB
  per preview (trailing rows dropped), 64 KB per listing (files that do not fit
  are listed without rows and point at the tool). The tool reads the turn
  snapshot under `reference/attachments/`, never the private store.
- Tool channel. `CodingAgentTurnRequest.tools` carries read-only tools the
  orchestrator lends one turn (`CodingAgentTool`). The BYOK driver offers them
  beside its file tools and never lets one replace a file tool. The `claude`
  and `codex` drivers have no tool channel, so every turn with sample data also
  gets the listing at `reference/sample-data.json`, removed again when the
  sample is gone. The turn prompt names the files, the tool and the reference
  file.
- Role guidance. The backend engineer derives `tests/fixtures/*.json` and
  `preview/seed.json` from the sample with invented names, contacts and
  identifiers, exports an idempotent `seed()` from `src/preview.ts`, and records
  `research-fixtures.json` and `adapters/<id>.recorded.json`. Its write paths
  gain `preview/**`, `src/preview.ts`, `research-fixtures.json` and
  `adapters/**`. The composed instruction is 5,172 characters against the
  5,500 budget.
- Preview seed (`server/preview-seed.ts`). After a generation starts, a draft
  with `preview/seed.json` (at most 1 MB) and `src/preview.ts` exporting `seed`
  gets `seed({ tenantId, accountId, data, databases })` with the preview
  workspace, the preview account, the parsed file and the preview database
  provider. A sha256 of both files is kept in the session data directory, so the
  seed runs again only after one of them changes. A failure becomes that
  module's preview error. `preview/` joins the preview revision, so an edited
  seed recomposes.
- Recorded adapters (`server/recorded-adapters.ts`). The `research` and
  `adapters` spec sections are read as plain YAML. A draft with a `research`
  section makes the preview compose `research.core` from the platform modules
  ahead of the drafts, and the preview settings store holds
  `research.core.adapter` at `recorded` and `research.core.recordedFixturesPath`
  at the absolute path of that module's `research-fixtures.json` for every
  workspace. A write of another value answers `409 SANDBOX_LIVE_ADAPTER_REFUSED`.
- Refusal. `research.adapter` set to `model-native` or `connector`, or an
  adapter entry without `recorded`, fails the `spec-schema` gate with
  `SANDBOX_LIVE_ADAPTER_REFUSED` naming the file and field. The gate still runs
  `spec validate` and appends its output. Delivery reruns the same gate. Preview
  module resolution throws the same code before a worker starts.
- Docs: `docs/sandbox.md`, section "Sample data and recorded adapters".

### Decisions

- Seeding goes through a `seed()` export, not the module's import port. The
  public `import.ports.v1` surface only registers ports; reading them is
  internal to `import.core`. A port write also needs a full `AuthPrincipal` and a
  job, and most drafts do not compose `import.core`. The preview would have to
  impersonate that capability.
- `PreviewSeedContext` is documented, not exported through the SDK. The platform
  API snapshot is unchanged, so there is no version bump.
- A `research` section without `adapter` is not refused. The preview holds the
  recorded setting either way.
- An adapter entry without `recorded` counts as live. RFC J5 says a gate refuses
  a live adapter, and such an entry could only call its connector.
- When several drafts declare research, the first in session order supplies the
  fixtures path, because the setting holds one path per workspace.

## Stream B: spec schema and skills

Branch `feat/rfc0006-spec-schema`.

### What landed

- `module-spec.schema.json` gains three optional version 2 sections,
  `research`, `adapters[]` and `templates[]`. A version 1 spec still rejects
  them key by key.
- `pnpm flowdular spec validate` checks what the schema cannot:
  `SPEC_ENTITY_UNKNOWN` for `research.evidenceOwner` and
  `templates[].inputEntity`, `SPEC_ADAPTER_ID_NAMESPACE`,
  `SPEC_ADAPTER_PORT_UNKNOWN`, `SPEC_ADAPTER_SCHEDULE_INVALID` (the `cron:`
  grammar of `modules/automations/src/domain/cron.ts`, checked for parity on 28
  expressions), `SPEC_ADAPTER_MAPPING_INVALID`, and `SPEC_DUPLICATE_ID` for
  adapter and template ids. `recorded` stays optional; the sandbox's own
  `spec-schema` gate refuses a live adapter with `SANDBOX_LIVE_ADAPTER_REFUSED`.
- `module new` writes, per section: `src/research.ts` and
  `research-fixtures.json` (one example query and page, on the first allowed
  domain); `src/adapters/<local id>.ts` and a recorded fixture stub at the
  declared `recorded` path, else `adapters/<local id>.recorded.json`, where the
  local id is the adapter id without the module id and dots become hyphens;
  `templates/<name>.md` from each template `body`. The TypeScript stubs hold the
  declaration (`as const satisfies` the contract type) and nothing that runs;
  `templates` joins the package `files` when a template exists. Two adapters
  that map to one stub or one fixture refuse the scaffold.
- `ModuleSpecResearch`, `ModuleSpecAdapter`, `ModuleSpecAdapterMapping` and
  `ModuleSpecTemplate` in `@flowdular/contracts`; platform API 0.1.15 with the
  snapshot regenerated.
- Skills: `spec-interview` asks about outside sources, other systems and
  documents; `module-new` and `module-update` carry the recipe and the touch
  lists; new `integration-adapter`, routed to `backend-engineer` for an explicit
  `$integration-adapter` (the default stays the module skill);
  `agent-tool-design` section 6 on research and evidence. Blueprint
  `.ai/blueprints/agentic-module` (status `draft`, documentation only).
  `docs/modules.md` documents the sections, the checks and the stubs.

### Where the contract did not match the tree

- The spec schema has no `imports` section. An import port is registered at
  runtime through `import.ports.v1` with the target id `<module id>.<key>`, so
  a source adapter's `port` is checked by owner: this module or a declared
  dependency.
- `import.ports.v1` exposes only `register`. Writing into a dependency's port
  has no public path until an adapters capability exists, so the skill tells
  the implementer to report it. The validator still accepts a dependency's
  port, as the contract states.
- The contract keyed `recorded` on a spec field `sandbox: true` that does not
  exist. After the sandbox stream landed its gate, no such field or CLI rule
  was added.
- Connector and operation keys follow `modules/connectors`
  (`^[a-z][a-z0-9-]{0,95}$`, `^[a-z][a-z0-9-]{0,63}$`); a port is at most 96
  characters like an import target id.

### Decisions the contract left open

- `research` requires `adapter` and `evidenceOwner`; `monthlyQueryBudget` is an
  integer of at least 1; domains are lower-case host names.
- `adapters[]` requires `id`, `direction`, `connector`, `operation`, `port` and
  at least one mapping; `schedule` is optional and `null` means on demand;
  `recorded` must be `adapters/<name>.recorded.json`.
- A mapping needs `from` unless it is a `constant` and `value` unless it is a
  `rename`.
- `templates[].body` must be `templates/<name>.md`; two templates may share a
  body.
- A sink's `port` is not checked. Only a module's own list export can be paged
  today, so restricting it to the module namespace is the likely next rule.
- The adapter fixture stub is `{ adapter, operation, calls: [{ input, body }] }`;
  nothing reads it yet, so its shape is not a contract until an adapter runtime
  does.

### Verification

`pnpm rules:check`, `reference:check`, `capabilities:check`,
`platform-api:check`, `pnpm validate` (including `blueprint validate --all`) and
`format:check` pass; typecheck passes. Every workspace suite ran with
`pnpm -r --no-bail test`: contracts 24, cli 208 and coding-agent 59 tests pass,
and the only failures are the 10 `packages/sandbox` `preview-worker` tests that
fail inside a worktree under `.claude/worktrees`. New checks were proven by
breaking each one and watching its test fail.

## Stream A: research.core and the harness native tool seam

RFC 0006 J1: the module `research.core` (0.1.0) in `modules/research`, the
native tool seam in `packages/harness` and `packages/kernel`, the public
egress capability of `connectors.core`, and the member defaults in `auth.core`.

### What landed

- Harness (`packages/harness/src/runtime.ts`). `AgentNativeTool` (`id`,
  `kind: 'web-search'`, `config`, `requiredPermissions`, optional `consent`,
  `resolveConfig` and `record`), `AgentProviderContext.nativeTools` and
  `reportNative`, and the event `tool.native`. A native tool shares the tool id
  space: `tools()` and `effectiveToolGrants` include it, so a definition allows
  and a run grants it by id. Its consent gate and `resolveConfig` run once when
  the run starts, inside the run deadline. A report is bounded (32 results,
  fields cut to their limits, entries without an http or https URL dropped,
  16 reports per tool per run), refused after the run settled, recorded as one
  event and handed to `record`, whose failure is a `tool.failed` event and never
  fails the run. The local simulation answers a granted web search from the
  absolute `research-fixtures.json` in `AgentExecutionRequest.nativeFixturesPath`
  and reports `NATIVE_TOOL_UNSUPPORTED` without one; the Vercel AI SDK provider
  reports every granted native tool as unsupported until the pass-through lands.
- Kernel. `PlatformToolRegistry.registerNative` and `listNative`, one id space
  with `register`. agents.core (0.12.10) passes the registered native tools to
  the harness; a run records the `tool.native` event like any other.
- `connectors.egress.v1` (connectors.core 0.1.8). `check(url)` answers
  `{ ok: true, url, addresses, lookup }` or `{ ok: false, reason }`: https on
  443, no address literal or local name, public addresses only, resolved through
  a c-ares resolver bounded to a few seconds, and a lookup that answers only the
  verified addresses. The template composition lists the new id.
- research.core. Tables `research_evidence`, `research_evidence_links`,
  `research_pages`, `research_queries`, `research_run_counters` with forced row
  security (migration 0001, mirrored). Capabilities `research.search.v1`,
  `research.fetch.v1`, `research.evidence.v1`. Adapters `model-native`
  (the provider searches through `research.web-search`; the search capability
  inside that run reads back the evidence of the same query), `connector`
  (instance from settings, operation `search`, input `{ q, limit }`, a declared
  result mapping) and `recorded` (absolute or workspace-relative
  `research-fixtures.json`, at most 1 MB). Budget reservation under a
  per-workspace advisory lock, released on any failure before the results
  commit, and the meter `research.core.queries`. Fetch through the egress
  capability only, robots.txt cached per host for an hour with a bounded match
  budget, one redirect with the domain rules, robots.txt and the egress policy
  applied again, size and time caps (the host resolution included), a readable
  text extractor, 24 hour page cache (never for a redirected page), 64 fetches
  per run. Agent tools `research.search` and `research.fetch` behind
  `research.consent`. Six endpoints, the `research.core.evidence` list export,
  three data classes, the Research screen (Administration, compliance) with
  Evidence and Queries tabs and the evidence drawer at `research-evidence?id=`.
- auth.core 0.13.14. `research.evidence.read`, `research.run` and
  `research.settings.manage` are owner defaults, the first two member defaults;
  migration 0034 grants them to existing memberships and built-in role rows
  with forced row security lifted on source and target.
- Enabled through `pnpm flowdular module enable research.core --apply`; the
  create-flowdular template lists the module with the same provides and
  requires, and `scripts/sdk-members.json` packs it into the SDK.
- Platform API 0.1.16 (0.1.15 is taken by Stream B on main).

0.1.8 `824862e0cabe356b8fd9b13ca091e4bbf08225f04e2167000109b13a855c24c8`, agents.core 0.12.10 `98f4dd43c9c7f0b146bcaa6fc85d06d5b05498a35107fea44eb9ad6622865bc2`, auth.core

### Where the contract did not match the tree

- `risk: 'external'` makes the harness demand a signed approval grant per call
  and the spec schema allows only `read` or `workspace-write` for an agent tool,
  so both tools are `workspace-write` behind the consent gate, as
  `connectors.call` is (D-RESEARCH-TOOL-RISK). `idempotency: 'none'` is not a
  value; the tools declare none.
- The meter key is `research.core.queries`: metering.core prefixes the module id
  and refuses dots in a key. The monthly limit is research's own setting, since
  a metering limit is set only by the operator.
- `documents.attachments.v1` has no create call, so `storeFullText` writes a
  `full_text` column on the evidence row and `document_id` stays empty.
- Columns added to the contract's lists: `research_evidence.full_text`,
  `research_pages.title` (a cache hit keeps the title) and
  `research_run_counters.updated_at` (the sweep needs a time).
- `requires` also names `connectors.egress.v1` and `exports.lists.v1`, which the
  module resolves; `check` is asynchronous and answers a pinned lookup, since a
  synchronous answer cannot resolve a host or close the rebinding window.
- `workspaceViewHref` takes no parameters, so another module links with
  `workspaceViewHref('research-evidence') + '?id=' + id`.
- `research.settings.manage` guards nothing yet: settings are written in
  Administration, Modules behind `system.settings.manage`.

### Decisions the contract left open

- A member search through the connector adapter is sent as caller `test`; the
  owner naming the instance is the consent (D-RESEARCH-MEMBER-CONNECTOR).
- Every search costs one unit, the recorded adapter included, so the budget can
  be exercised offline; a model-native read back costs nothing.
- The member attach route refuses an owner module in whose namespace the member
  holds no scope (`RESEARCH_ATTACH_FORBIDDEN`); the capability trusts its
  calling module.
- robots.txt answering a 4xx admits every path; one that cannot be read refuses
  the fetch (`RESEARCH_ROBOTS_UNAVAILABLE`) and is not cached.
- Erasure removes the account from evidence and member queries and keeps the
  rows; the page cache is cleared.

## Wave 2a, Stream D

Branch `feat/rfc0006-provider-native`: the model-native web search pass-through
in `packages/ai-provider` and `packages/harness`, the agents.core outbound
address block, and the sandbox preview integration test wave 1 left open.

### What landed

- `packages/ai-provider/src/web-search.ts`. `webSearchPassThrough(kind, config)`
  answers the provider's own tool: Anthropic
  `anthropic.tools.webSearch_20250305({ maxUses, allowedDomains | blockedDomains })`
  and OpenAI `openai.tools.webSearch({ filters })` with the responses option
  `maxToolCalls`; null for `azure`, `openai-compatible` and `vercel`. `maxUses`
  is an integer from the native tool config, default 5, clamped to 16.
  `webSearchReporter` is a language model middleware that collects the
  provider-executed results of the pass-through tool and the call's citations
  and hands one report per search to the caller when the model call's stream
  finishes. `resolveLanguageModel` now declares `Exclude<LanguageModel, string>`,
  which every branch already returned, so the model can be wrapped.
- `packages/harness/src/vercel-ai-provider.ts`. The first granted `web-search`
  native tool goes to the provider under its provider-safe id (collisions refused
  like any tool), the model is wrapped with the reporter, and each report goes
  through `reportNative`, so the harness records `tool.native` and the tool's
  `record` runs (research.core keeps the query and evidence). Every other native
  tool, and every native tool on Azure, OpenAI-compatible or Vercel AI Gateway,
  reports `NATIVE_TOOL_UNSUPPORTED` and the run goes on. A native report the
  harness refuses keeps the harness code instead of being reclassified as a
  provider failure.
- Degrading on a refused tool (coordinator follow-up). `webSearchRefusal(error)`
  answers `PROVIDER_WEB_SEARCH_DISABLED` only for the SDK's `APICallError` with
  status 400 or 403 whose error body (`error.type` absent,
  `invalid_request_error` or `permission_error`) has a message naming web
  search (`/web[\s_-]?search/i`, which also covers the tool types
  `web_search_20250305` and `web_search`). The reporter catches that refusal
  around the model call, reports it once, retries the same call once without
  the pass-through tool and without OpenAI's `maxToolCalls`, and leaves the tool
  out of every later call of the run. The run then goes on without web search,
  so research.core's chain can use its next adapter. Any other error, a generic
  400 included, fails the run as before. `AgentNativeReport`'s unsupported form
  gains an optional `detail` code, which the harness records on the `tool.native`
  event when it has the shape of a code (`^[A-Z][A-Z0-9_]{2,63}$`).
- Mapping to `ResearchResult`: `url`; `title` from the result, else the citation;
  `snippet` from Anthropic's `cited_text` (OpenAI citations carry none);
  `publishedAt` from Anthropic's `page_age` verbatim; `source` is the provider
  kind. Anthropic takes the query from the call input, OpenAI from
  `action.queries[0]`, then `action.query`.
- agents.core 0.12.11. `outbound-policy.ts` carries `blockedIpv4`, `ipv6Bytes`
  and `blockedAddress` byte for byte from connectors.core, and
  `assertPublicHost` refuses through `blockedAddress`. The block is wrapped in
  one comment naming the three owners, identical in connectors.core,
  notifications.core and agents.core (connectors and notifications otherwise
  unchanged, still byte identical to each other). `tests/address-block.test.ts`
  has the same 33 cases; 16 of them fail against the old block. Spec scenario
  `AGENTS-PROVIDER-ADDRESS-BLOCK`.
- `packages/sandbox/tests/preview-worker.test.ts`: a session whose draft spec
  has `research: { adapter: recorded, evidenceOwner: case }` composes
  `system.core`, `research.core` and the draft; a draft route reads
  `research.core.adapter` as `recorded` and `recordedFixturesPath` as the
  draft's `research-fixtures.json`; a signed-in `POST /api/research/search`

- `@ai-sdk/anthropic` 4.0.46: `webSearch_20250305` sends

### Decisions the contract did not settle

- Reports are sent when a model call's stream finishes, not as each result
  arrives: citations follow the results, and because the SDK runs the model's
  tool calls only after the stream closed, `research.search` in the same run
  still reads the evidence back. A test with a slow report proves the order.
- `source` is the provider kind (`anthropic`, `openai`), not the tenant's
  connection id, which tells a reader nothing.
- `web_search_20250305`, not `20260209`: it works on every catalog model,
  `claude-haiku-4-5` included, with no beta header and no implicit code
  execution.
- Anthropic refuses `allowed_domains` together with `blocked_domains`, so an
  allow list is sent alone and a block list only without one, for both
  providers. research.core still filters the recorded results by both lists.
- OpenAI gets `max_tool_calls` from `maxUses` (built-in tool calls per
  response); the contract named max uses for Anthropic only.
- One provider web search per request; a second granted web-search native tool
  reports `NATIVE_TOOL_UNSUPPORTED`.
- A search the provider answered with an error is not reported (no budget unit),
  and neither is an OpenAI `openPage` or `findInPage` action. A search that
  returned no URLs, such as an OpenAI search without sources, takes the URLs the
  call cited.
- At most 16 reports per run (the harness limit): searches past the last slot
  merge into it, and later ones are not recorded, so a long run never fails on
  the report limit.

### Open points

- The refusal is recognised from the provider's error message naming web
  search, since neither provider documents a dedicated error code for it. A
  provider that refuses the tool with a message that does not name it still
  fails the run.
- `web_search_20260209` (dynamic filtering) on the newer models needs a model
  gate in the catalog.
- The worktree `preview-worker` failure comes from `bin/register-types.mjs`
  treating only `MODULE_NOT_FOUND` as "no SDK"; accepting `ERR_ACCESS_DENIED`
  there is the candidate fix. Sandbox sources are outside this stream.
