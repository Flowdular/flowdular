# RFC 0006 J3: documents from templates (2026-09-16)

Branch `feat/document-templates`. RFC 0006 J3 in `modules/documents`, with the
two new permissions in `modules/auth`, the preview path in `packages/sandbox`
and the composition lists of the platform and the create-flowdular template.
The owner decided to build J3; the coordinator chose a pure JavaScript
renderer inside the platform process behind a renderer interface.

## What landed

- Template language (`src/domain/template-language.ts`, browser safe). A body
  is parsed into blocks and inline nodes before any value exists: headings 1 to
  3, paragraphs with bold, italic, inline code and links (printed as the text
  and the URL in parentheses), bulleted and numbered lists with one nesting
  level, block quotes, a rule, `---pagebreak---` and GFM pipe tables. `{{#each
path}}`, `{{#if path}}`, `{{else}}` and the closing tags stand on lines of
  their own, at block level or between table rows. Placeholders `{{ path }}`
  become nodes of their own and are substituted into text runs by the evaluator
  (`template-evaluate.ts`), so nothing an input carries is read as Markdown.
  Refused with a stable code and the 1-based line: raw HTML, images, footnotes,
  reference definitions, fenced and indented code, setext headings, headings
  past level 3, a second list level, a nested quote, a malformed table, a block
  tag inside a paragraph, an unbalanced or too deep block (8), an unknown
  formatter, a malformed or triple-brace placeholder, `@index` outside an each,
  and every path the input schema does not hold or holds with the wrong type.
- Formatters: `money: currency` (minor units, ISO 4217 checked against
  `Intl.supportedValuesOf`), `number: n` (0 to 6), `date` and `datetime` (the
  workspace zone from `system.core.timeZone`, a `YYYY-MM-DD` date not shifted,
  a datetime only with a zone designator), `upper`, `yesno` (Yes/No, Tak/Nie).
- Input schema subset (`template-schema.ts`): object, string (maxLength,
  enum), number, integer, boolean, array of an object or a scalar, required,
  title and description; 4 levels, 64 properties; anything else is
  `TEMPLATE_SCHEMA_INVALID`. `validateTemplateInput` answers up to 20 issues
  with their paths; `templateInputSchemaFromFields` builds a schema from spec
  entity fields.
- Layout (`template-compile.ts`): A4 or Letter, margins 5 to 60 mm, a one-line
  header and footer with placeholders plus `{{page}}` and `{{pages}}`, a title
  that becomes the document title and the file name.
- Bounds: body 65536 characters, 2000 repeated rows or blocks, 1000000 printed
  characters, 200 PDF pages, 256 KiB of input, 10000 characters per string,
  2000 array items.
- Renderers (`src/services/render/`) behind `DocumentRenderer` keyed by format.
  PDF through pdfmake's prebuilt bundle (`build/pdfmake.js`), whose virtual file
  system is given only the four Roboto faces and whose URL and local access
  policies refuse everything; tables repeat their header row and
  keep a row whole, every page gets its header and footer, and the page bound
  is enforced from the footer callback before a byte is written. DOCX through
  docx with numbering per list, `tableHeader` rows, `PAGE` and `NUMPAGES`
  fields, then repacked with `[Content_Types].xml` as the first entry, because
  the storage port recognises an OOXML document by that entry and docx writes
  it tenth. Both libraries are imported lazily on the first render.
- Capability `documents.templates.v1` (`domain/templates.ts`,
  `services/templates-capability.ts`): `register(moduleId, templates)` while the
  platform composes (key inside the module namespace, everything validated at
  once, at most 256, `TEMPLATE_REGISTRATION_INVALID` naming the first issue and
  its line, sealed when documents.core starts), `render(request)` and
  `status(tenantId, jobId)`.
- Versions (`services/templates-service.ts`). A workspace uses the module
  default until it renders or edits; then the default is kept as version 1.
  Save appends an `edit` after checking the expected version
  (`TEMPLATE_VERSION_CONFLICT` 409) and a change (`TEMPLATE_UNCHANGED` 409);
  revert appends a copy of the default (`revert`) or of an earlier version's
  body and layout (`edit`). A workspace whose current version is `module` or
  `revert` follows a changed default with a new `module` version on its next
  render; an `edit` stays.
- Renders. The input is validated and evaluated against the version the render
  will use before anything is written. The render row is unique by workspace,
  template key, version, owner module, record reference, format and input
  digest (sha256 of canonical JSON): a repeat answers the same row, a failed
  row is queued again, a succeeded row whose document was deleted is queued
  again with the next generation. A render of at most 50 repeated rows and 16
  KiB of input is claimed and performed within the call; the rest runs on
  `documents.core.render` (routing read on the background role, claim token,
  heartbeat, five minute stale takeover, `CLAIM_LOST`, three attempts then
  `TEMPLATE_RENDER_FAILED`). The object id is the render id (plus `-g<n>` for a
  later generation); the `documents_files` row is inserted in the transaction
  that marks the render succeeded while the claim holds, so a process dying
  after the object was written repeats the render under the same id and a late
  settle changes nothing. The workspace quota applies (`QUOTA_EXCEEDED`), an
  infected verdict fails the render and removes the object, the input is
  cleared when the render settles.
- Migration 0005 (mirrored): `document_templates`, `document_template_versions`,
  `document_renders` and `document_render_keys` with forced row security, the tuple, pending and
  settled indexes, and a background policy and column grant for `id,
tenant_id, status, created_at, claimed_at` of queued and running renders.
- Data classes `documents.core.templates` (kept, exported) and
  `documents.core.renders` (90 days, sweep of settled rows, exported without
  the input).
- Routes behind `documents.templates.read`: `GET /api/documents/templates`,
  `/detail`, `/versions` (keyset, 50), `/version`, and `POST /preview` (renders
  the draft to bytes, stores nothing). Behind `documents.templates.manage`:
  `POST /save` and `/revert`. Every POST passes the CSRF check first; refusals
  carry `issues` with lines or input paths.
- Agent tool `documents.render`: `workspace-write`, `idempotency: required`,
  `target-ledger`, requires `documents.templates.read` and
  `documents.files.manage`, tenant and account from the run. The harness key is
  bound in `document_render_keys` to a planned render id before the render row
  is written, with the request digest, so a retried call answers the render it
  first reached even after the template gained a version, and a key reused for
  another request answers `TEMPLATE_RENDER_KEY_REUSED` (409). The agent tool
  `documents.render-status` (`read`, `documents.templates.read`) reads a job by
  id.
- Preview is bounded to two renders at a time per process
  (`TEMPLATE_PREVIEW_BUSY`, 429), because laying out a document holds the event
  loop.
- Permissions: auth.core 0.13.18, migration 0036 grants both scopes to owners
  and `documents.templates.read` to members, in memberships and built-in role
  rows.
- Sandbox: `resolvePreviewModules` composes documents.core ahead of a draft
  whose spec declares `templates[]`, so the preview registers and renders
  through the same renderer; nothing extra is seeded.
- Versions through the CLI: documents.core 0.3.0 (minor; import.core's range
  retargeted to `^0.3.0`), auth.core 0.13.18. `module sync --apply` regenerated
  the platform composition and the create-flowdular template carries the same
  provides list. No package surface changed, so the platform API stays 0.1.19.

## Dependencies

- `pdfmake` 0.3.11 (MIT, 15.3 MB unpacked including browser builds and source
  maps, released 2026-06-12, 14 releases in 2026, four maintainers). Chosen for
  tables that break across pages with repeated header rows, dynamic headers and
  footers with the page count, and embedded TrueType fonts, which pdfkit alone
  leaves to the caller. It brings `pdfkit` 0.19.1 (MIT), `fontkit`, `linebreak`
  and `xmldoc` (SVG, unused). It ships the Roboto family (Apache-2.0) as base64
  in `build/vfs_fonts.js`, which covers Latin Extended-A, so no font package is
  added. Rejected: `pdf-lib` (last release 2022, no layout), `jspdf` (30 MB,
  browser first, tables through a plugin).
- `docx` 9.5.1 (MIT, 4.6 MB, dolanmiu). 9.5.3 and later declare
  `@types/node ^25` as a runtime dependency, which pulled a second major of the
  Node type definitions into the workspace and moved vite's peer resolution in
  unrelated importers; 9.5.1 declares `^24` and resolves to the pinned 24.13.3.
  The releases after it add content controls, endnotes, track changes and
  embedded font naming, none of which the renderer uses.
- No `@types/pdfmake`: its `@types/node *` dependency has the same effect, and
  the renderer reaches two entry points typed in `render/pdfmake.d.ts`.

pnpm installed both without a `minimumReleaseAgeExclude` entry.

## Where the contract did not match the tree

- The scaffold writes an HTML comment into `templates/<name>.md`, and the
  contract refuses HTML. Comments on lines of their own are dropped instead of
  refused; an inline comment is still HTML.
- The platform server build cannot take pdfmake's Node entry: fontkit pulls in
  `brotli/dec/dictionary-data.js`, a 122000 element array literal, and the
  server bundle build stops on it with `RangeError: Maximum call stack size
exceeded` from the octane plugin. The renderer loads pdfmake's prebuilt
  `build/pdfmake.js` instead, which carries the same pdfkit and fontkit with
  brotli's compact dictionary, so no platform or consumer build configuration
  changes.
- The storage port accepts a DOCX only when `[Content_Types].xml` is the first
  ZIP entry, which docx does not produce, hence the repack.
- `document_renders` needs the input to render on the job runner and a
  generation to render again after a deletion; both are columns beyond the
  contract's list. A fourth table, `document_render_keys`, is the tool's key
  ledger: the render tuple alone let a retried call render a newer version. `document_template_versions` carries `origin` and
  `content_sha256` for the follow-the-default rule.
- A template body cannot be read from `templates/<name>.md` at runtime: the
  production server is one bundle and the sandbox worker loads TypeScript
  only. The skills describe `src/templates.ts` mirroring the file with a test,
  the way migrations are mirrored.

## Decisions the contract left open

- Inline rule: at most 50 repeated rows and 16 KiB of input, both measured on
  the input before rendering; pages cannot be measured before layout.
- `@index` counts from 0 as in Handlebars; `@number` counts from 1 for printed
  row numbers. A path is searched from the innermost each item outwards.
- The idempotency tuple adds the owner module and the format to the contract's
  key, version, record reference and input digest.
- A workspace edits the body and layout only; the input schema, locale and
  format stay the module's.
- Preview requires `documents.templates.read`, since it stores nothing.
- The agent tool requires `documents.templates.read` and
  `documents.files.manage` without an owner-module record check, because its
  input comes from the run and attaching is workspace-wide under
  `documents.files.manage` (D-DOCUMENTS-ATTACH-AUTHORITY).
- DOCX names Roboto without embedding it; Word substitutes a font that covers
  Polish when Roboto is absent. The page bound applies to PDF only.
- The Templates screen lives in Administration, section platform.

## Review

The auto-review phase ran as a separate read-only agent and blocked the first
cut on five findings, all fixed with tests:

- A body of unmatched brackets or underscores parsed in quadratic time (14.5 s
  at the size bound) and nested link labels overflowed the stack, reachable by
  a member through Preview. The inline parser now indexes delimiter runs,
  matching brackets and the next parenthesis and whitespace once per paragraph
  and finds closers by binary search, styles nest at most 8 deep, links do not
  nest, and the block patterns whose backtracking was quadratic on long space
  runs (heading, rule, block tag, hard break) are hand written. Eight hostile
  bodies at the size bound each parse within a second.
- A repeated `documents.render` call could attach a second document after the
  template gained a version: the key ledger above.
- An inline render whose caller aborted stayed `running` for the stale window:
  it is handed back at once.
- A title cut in the middle of a surrogate pair broke the preview's
  content-disposition: the file name is cut by code point.
- A render that failed after an attempt had stored its object left the object
  behind: a fenced failure removes it; a lost claim never does, since the
  winner's document shares the object id.

The re-review passed the five fixes and found one more: a key bound to a
planned render whose row was never written stayed on that id, so a later retry
after a version change could render again. The key now follows the render the
retry writes, and the retention sweep removes a key that names no render once
it is past the cutoff.

Also added: cross-workspace inserts refused on all four tables, and a runner
whose heartbeat reports the claim lost aborting without settling.

## Open points

- The Templates screen was checked by typecheck, compilation and presentation
  tests, not in a running browser: that needs a signed-in account in a local
  app, which this stream did not create. Whether Chrome opens the PDF preview
  from a blob URL under the platform CSP (`object-src 'none'`) is unverified.
- A preview holds the event loop while it lays out a document (about 2.5 s for
  2000 rows); the bound of two concurrent previews limits the queue, not the
  blocking.
- A render swept after 90 days no longer deduplicates: the same input renders a
  new document.
- The sandbox preview composes documents.core for a spec with `templates[]`,
  but the preview worker cannot start inside a worktree, so the render through
  a preview was not run here.
- DOCX headers, footers and page numbers are not read by the J2 extractor; the
  tests read those parts of the package directly.
